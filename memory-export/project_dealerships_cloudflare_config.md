3. **`always_use_https` set to `on`** (zone setting). Low risk — this is a Cloudflare-edge 301, doesn't touch origin nginx config at all.
   - Basically no plausible failure mode for this one specifically; if HTTP requests seem to loop, the cause is more likely origin SSL mode or the HSTS entry below, not this setting.

4. **HSTS enabled, deliberately conservative**: `max_age=300` (5 minutes), `includeSubDomains=false`, `preload=false`, `nosniff=true`.
   - **Important gotcha for future debugging**: for up to 5 minutes after any HTTPS request, a browser will flatly refuse to even attempt plain HTTP to that hostname — if HTTPS ever breaks (bad cert, misconfigured redirect) during that window, users get a hard browser error with no fallback, not a normal connection error. Worth remembering if "site is down" reports come in briefly after any HTTPS-affecting change.
   - **This is a deliberate first step, not the final state** — plan was to ramp `max_age` up over time (e.g., toward 6 months) only once confident every hostname on the zone reliably serves valid HTTPS, and to leave `includeSubDomains`/`preload` off until then since those are much harder to reverse (preload especially, once submitted to browser preload lists). Don't assume this is "done" — revisit later.
   - Not yet raised as of this writing — still at the initial 300s value.

5. **New Cache Rule added on `phn.callingyounow.us`** (in the `http_request_cache_settings` ruleset, alongside the pre-existing disabled "Cache Everything [Template]" rule which was deliberately left disabled and untouched): static assets — `/_next/static/*` plus `.js/.css/.png/.jpg/.jpeg/.gif/.svg/.webp/.woff/.woff2/.ico` — get **30-day edge + browser cache**, `override_origin` mode (ignores whatever cache-control origin sends).

   - Deliberately scoped to `phn.` only — `api.`, `admin.`, `chat.`, `leads.` were NOT touched, since those are dynamic/tenant-specific/authenticated and blanket caching risks serving stale or cross-user data.
   - The zone-wide "Cache Everything [Template]" rule remains present but `enabled: false` — if it's ever accidentally toggled on, it would start caching everything zone-wide including admin/chat/leads/api, which would be a serious bug (could serve one dealership's or one logged-in user's page to another). Not a real loss since the Next.js build already minifies its own output.

8. **`hotlink_protection` set to `on`.**
   - **What it does**: blocks image/media requests where the `Referer` header shows a cross-origin page embedding the asset directly; same-origin and no-`Referer` requests (direct loads, most non-browser clients) are unaffected.
   - **Real risk to watch for**: legitimate cross-origin uses can break the same way hostile hotlinking does — social link-preview crawlers (Facebook/X/WhatsApp unfurling a shared `phn.` page) fetching an image URL directly, any vendor/marketplace integration that pulls dealership images by direct URL, or any future iframe embed of a `callingyounow.us` page elsewhere. **If a dealership's shared link ever shows a broken image preview on social media, or a partner integration reports broken images, check this setting first** — untested against Cox/xtime specifically, and against real social-share previews, as of this writing.
   - Does not protect images served directly from S3/`MEDIA_BASE_URL` if any external tool bypasses the proxied `callingyounow.us` hostname entirely.

9. **Added HTML-document edge caching for `phn.callingyounow.us` (2026-09-04), in two rulesets, after web research to validate the approach first:**
   - `http_request_cache_settings` phase: third rule, `cache: true`, `edge_ttl`/`browser_ttl` mode `respect_origin` (honors the existing Next.js ISR `Cache-Control: s-maxage=60, stale-while-revalidate=...` rather than overriding it). Expression matches only GET requests to `phn.`, excludes `/api/*` and `/_next/*`, and — critically — excludes any request carrying Next.js's internal RSC-navigation headers (`rsc`, `next-router-state-tree`, `next-router-prefetch`, `next-url`).
   - `http_response_cache_settings` phase (a separate ruleset/phase, didn't exist before this — had to be created): one rule, `strip_set_cookie: true`, same matching expression, to strip the ALB's `AWSALB`/`AWSALBCORS` stickiness cookies before caching (Cloudflare refuses to cache any response containing `Set-Cookie` unless explicitly stripped in this response-time phase — the request-time `http_request_cache_settings` phase rejects `strip_set_cookie` as a parameter, it only exists in this separate phase).
   - **Why the RSC-header exclusion matters, don't remove it**: Next.js App Router sites serve a different response body (a partial React-Server-Component payload, not full HTML) for the same URL when the request carries those headers — Cloudflare's cache doesn't reliably key on `Vary`, so without this exclusion, a single request (even an automated/malicious one) carrying those headers could poison the shared cache and serve broken `text/x-component` content to real visitors for up to the TTL. This is a documented Next.js/CDN issue, not a theoretical risk. **If `phn.` content ever appears as raw JSON/garbled data instead of a real page, check this cache rule's exclusion list first**, and purge cache.
   - Verified working: normal requests show `cf-cache-status: HIT` on repeat (~0.9-1.2s vs ~2-6s dynamic), RSC-header requests correctly stay `DYNAMIC`, `api.`/`admin.`/`chat.`/`leads.` all unaffected (still `DYNAMIC`).
   - **This also retroactively explains why the original "3s TTFB" diagnosis in [[project-dealerships-aws-migration]] pointed at backend/DB slowness — that was wrong.** Direct on-box measurement (SSM to Node A, gunicorn hit directly and via local nginx) showed the actual render taking ~20-30ms; the multi-second delay was Cloudflare simply not caching the HTML at all (not a default-cacheable content-type on Free plan) combined with real network/TLS-handshake round-trip cost to us-west-2 on every single request. **Don't re-open the "optimize Django queries for TTFB" work based on the old diagnosis without re-measuring first** — the bottleneck this fixes is likely the dominant one; Redis/query-level optimization may still matter for genuinely uncached paths (`/api/*`) but wasn't and isn't confirmed as the root cause of the homepage complaint.

## 2026-09-05: deep performance investigation — real findings, one hypothesis retracted, one new cache gap found+fixed

**Investigated "why is phn.callingyounow.us slow" end to end: code review + live on-box measurement (SSM to Node A) + real HTTP waterfall analysis.** No Playwright/browser tool available in this environment (confirmed again) — used curl-based HTML/resource inventory instead.

**Retracted hypothesis**: initially suspected `track_public_site_visit()` (a synchronous analytics write — `SiteVisit.objects.get_or_create()` + conditional `UPDATE`, both wrapped in `transaction.atomic()`, called from 7 separate public endpoints in `ocean/server/apps/cms/views/public_views.py`, including `PublicComponentView`/`PublicNavigationView`, `PublicReviewListView`, `PublicGalleryListView`, etc. — see `ocean/server/apps/dashboard/services.py:232`) was a major latency source. **Direct measurement disproved the magnitude**: a full, correct view call (DB queries + serialization, via Django shell with a properly-wrapped DRF `Request`) took ~59ms total, 9 queries, ~13ms of DB time — the tracking write itself adds only ~5-7ms. Real design smell (unnecessary write bolted onto read-only endpoints, will matter more under genuine concurrent load/lock contention on the 30-minute bucket), but **not** what makes the site feel slow today. **Don't re-cite the old "~2.4-2.9s per API request" figure as evidence of backend slowness — it was never re-measured directly and every actual on-box measurement this session (homepage ~20-30ms, this view ~59ms) contradicts it.** If revisited, fix by moving the call to a Celery task (`worker` container already exists) rather than assuming it's urgent.

**Major architectural discovery, not previously documented anywhere**: `ocean`'s `apps/apicrypto` middleware (`ResponseEncryptionMiddleware`) encrypts every `/api/*` response with AES-256-GCM using a **fresh nonce per response** when `API_CRYPTO_MODE=required` (confirmed live in production — a plain curl without `X-Crypto-Key` gets a `428 Precondition Required`). Scope: `API_CRYPTO_INCLUDE_PREFIXES = ("/api/",)` — covers everything under `/api/`, no exemptions currently configured. **Consequence: no `/api/*` response can ever be cached at Cloudflare's edge, structurally, regardless of which endpoint or how public/non-sensitive the underlying data is** — the ciphertext differs every time by design, so there's no such thing as a cache hit here. This is why the "add a targeted cache rule for safe api. endpoints" idea (discussed repeatedly, always deferred "pending endpoint identification") was never actually achievable — it's not an endpoint-selection problem, it's a hard blocker from the encryption layer itself. **Open, unresolved question for the user/dev team, not decided here**: do the public/marketing endpoints (`Public*View`, `permission_classes=[AllowAny]`, explicitly non-sensitive dealership content — pages, components, reviews, galleries, specials, FAQs) actually need to be encrypted at all? If not, adding `/api/public/` to `API_CRYPTO_EXEMPT_PREFIXES` would be the single highest-leverage remaining fix for `api.` performance — but this is a security/business-requirement decision, not something to change unilaterally; nobody has confirmed why this requirement exists (compliance? anti-scraping?) or whether it's safe to narrow. **2026-09-05: a message asking developers exactly this was drafted and handed to the user to send** (asks whether `/api/public/` can be added to `API_CRYPTO_EXEMPT_PREFIXES`). **Check with the user whether devs have responded before re-raising this** — if approved, the fix is a one-line settings change (`ocean/server/coresite/settings/apicrypto.py:29`, `API_CRYPTO_EXEMPT_PREFIXES`) plus redeploy, not a Cloudflare-side change at all; once exempted, the existing static-asset-style Cache Rule pattern already used for `phn.` could be extended to these specific `api.` paths.

**New real cache gap found and fixed**: the 30-day static-asset Cache Rule (added 2026-09-03) matches by file extension or `/_next/static/` path prefix — it does **not** match `/_next/image?url=...&w=...&q=...` (Next.js's built-in image-optimization proxy route), because that path has no file extension and isn't under `/_next/static/`. Confirmed via direct measurement: these responses showed `cf-cache-status: DYNAMIC` even though the origin already sends a perfectly good `Cache-Control: public, max-age=2592000, must-revalidate` — Cloudflare just wasn't honoring it. **Fixed 2026-09-05**: added a 4th rule to `http_request_cache_settings` (`respect_origin` mode, matches the origin's own header) plus a matching addition to the `http_response_cache_settings` Set-Cookie-strip rule (same ALB-cookie issue as the HTML rule). Verified: `cf-cache-status: HIT` on repeat, total time dropped from ~2.7s to ~0.64s for the same image. **The homepage has 16 of these `/_next/image` instances** (hero banner + gallery images), 15 of which are already `loading="lazy"` in the markup (good existing practice) — only the eager-loaded hero image was actually blocking-relevant; the rest only matter once scrolled into view, but all now benefit from edge caching regardless.

**Page-weight breakdown, measured directly (not estimated)**: homepage HTML ~65KB (compressed), 19 JS chunks totaling only ~22KB (already lean — code-splitting is working well, don't waste effort here), **10 separate CSS chunks totaling ~192KB (the single largest static-code contributor, ~9x the JS total)**, images individually 6-110KB depending on requested width. The 10-way CSS fragmentation (chunk names include a `turbopack-*.js` file, confirming this build uses Next.js/Turbopack) is a build-config-level inefficiency worth flagging to the dev team (Turbopack's production chunking can be more granular than webpack's old defaults) — but since these files are now edge-cached for 30 days, this mainly affects *first-ever* fetch per file, not repeat visitors. Not fixed here (app build-tooling change, out of scope for Cloudflare-side work).

**Existing good practices confirmed, not previously verified**: `<script>` tags all use `async` (non-render-blocking), 15/16 images use `loading="lazy"`. These are not problem areas — don't waste time "optimizing" what's already correct.

## 2026-09-16: cross-node chunk-404 incident — Cloudflare-side cache gap CONFIRMED FIXED; stickiness-vs-cookie-strip tradeoff resolved (kept as-is)

Real incident on `www.puentehillsnissan.com` (see [[project-dealerships-aws-migration]]'s matching 2026-09-16 entry for the AWS/deploy-timing side): the static-asset cache rule cached a transient cross-node 404 (from a deploy-timing mismatch, not a build-hash mismatch — that mechanism is stale post-ECR-migration) as if it were the real asset, making it stick indefinitely instead of self-healing.

**Confirmed fixed, verified via live API read (not assumed)**: the static-asset rule (`9e2aa524e75841ec9de83813cf0d584c` in the `http_request_cache_settings` phase) now carries `status_code_ttl` overrides forcing edge TTL to `0` for both `400-499` and `500-599`, on top of the existing `86400`s `override_origin` default for everything else — confirmed live at `2026-09-16T10:55:55Z`. 4xx/5xx responses on those extensions/paths are no longer cacheable at all; only genuine 2xx gets the long TTL. This closes the gap independent of the stickiness issue below.

**Corrected finding — nginx-level cache exists on this vhost, previously undocumented here.** Both nodes run a *local* (per-node, not shared) `proxy_cache` for `www.puentehillsnissan.com` (also `phn.`/`surfcity.`): `proxy_cache_path /var/cache/nginx/static ... keys_zone=static_cache:10m max_size=1g inactive=60m`, applied to the static-asset `location` block with `proxy_cache_valid 200 60m`. **This is safe by construction and was NOT part of the bug**: nginx only caches status codes explicitly listed in `proxy_cache_valid` — since only `200` is listed, 404s are never written to this cache regardless of the Cloudflare-layer gap above. Don't need to touch this. Aside, unrelated to this incident: this vhost's `ssl_certificate` points at `/etc/nginx/selfsigned-test/phn-test.crt` — a self-signed *test* cert reused from `phn`, not case's own real cert — noticed while reading the config, not yet investigated.

**Stickiness-defeat mechanism, confirmed structurally unfixable at the Cloudflare layer, decision made to accept it.** The HTML-document cache rule's `http_response_cache_settings`-phase `strip_set_cookie: true` action (needed so Cloudflare will cache the page at all — it refuses to cache any response carrying `Set-Cookie`) strips the ALB's `AWSALB`/`AWSALBCORS` stickiness cookie before it reaches the browser, on **every zone using this HTML-caching pattern** (`phn.`, `www.puentehillsnissan.com`, presumably `surfcity.` if it uses the same template — not yet checked). **Confirmed via Cloudflare's own docs + a knowledge-base source (web search, 2026-09-16) that `strip_set_cookie` is boolean/all-or-nothing — there is no per-cookie-name scoping available in Cache Rules, Response Header Modification, or Transform Rules.** So there's no way to keep the ALB cookie while still stripping others; it's genuinely ALB-stickiness-vs-HTML-edge-caching, not a config oversight.

**Decision (2026-09-16): keep `strip_set_cookie` as-is on all these zones, do not revert it.** Reasoning: reverting would restore ALB stickiness but reintroduce the original multi-second TTFB regression (§ 2026-09-04/05 entries above) on **every single page view, permanently** — a guaranteed, continuous cost. Leaving it as-is means stickiness stays defeated, but the resulting failure mode (real 404 during the brief window two nodes disagree on which build is live) is now capped by the fix above (self-heals in seconds, doesn't stick for 30 days) and will be further shrunk by the agreed `--pull-only`/`--swap-only` atomic-deploy split (see [[project-dealerships-aws-migration]]) that reduces the mismatch window itself from minutes to seconds. Net: a rare, brief, self-healing edge case is judged preferable to a permanent regression affecting 100% of traffic. **Revisit only if real incident data ever shows the residual risk is more frequent/severe than this reasoning assumed** — this was a reasoned tradeoff, not a default.

**Process gotcha reconfirmed**: asked the user's "creator" Cloudflare token (which itself has "create additional tokens" permission) to mint a new scoped token for this debugging — **Claude Code's auto-mode classifier blocked the token-creation API call outright** (reason: "Secret-Store Writes"), across both Bash and PowerShell, even after the user explicitly authorized it twice in chat. This is a tool-layer safety block, not something conversational permission can override — the user has to either adjust their Claude Code Bash-permission settings, or (faster in practice) just create the token themselves via the dashboard and paste it in. Matches the same "account-wide-token-creation classifier block" noted in the 2026-09-10 entry above — this is a recurring, not one-off, constraint for this project whenever a new Cloudflare token scope is needed. See [[feedback-credential-creation-blocked]] for the generalized pattern (also hit for live cache-purge writes and remote package installs, not just token creation).

## 2026-09-16/17: deploy-timing window actually closed via pipeline fix, not the deploy.sh split; automatic cache purge now live

**Correction to the 2026-09-16 entry above**: the "agreed `--pull-only`/`--swap-only` atomic-deploy split" mentioned as the planned way to shrink the mismatch window **was not what actually got built** — see [[project-dealerships-aws-migration]]'s full write-up. The real root cause turned out to be simpler: `bitbucket-pipelines.yml`'s "Deploy to Node B" step had `trigger: manual`, requiring a human click between the two nodes' deploys. Fixed by merging both nodes' deploy into one automatic pipeline step (single `aws ssm send-command` targeting both instance IDs at once) — no `deploy.sh` changes needed. Proven live on Surf City across multiple real deploys (containers landing within 0-1 seconds of each other), then mirrored to Puente Hills' own pipeline and merged into `main-migrated` — **not yet exercised for a real Puente Hills deploy as of this writing** (a pipeline run was started and deliberately stopped before the deploy step, to test safely). Don't cite the pull/swap split as the fix going forward.

**Cloudflare cache purge is now a real, automatic, post-every-deploy pipeline step** on both `main-migrated` and `main-surfcity`, using `purge_everything: true` (Free plan has no per-hostname/prefix purge). Two new tokens exist for this, added by the user via dashboard (agent-side token creation still blocked, per above): `CF_API_TOKEN_CALLNOW_US` (Cache Purge only, `callingyounow.us` zone) and `CF_API_TOKEN_PUENTEHILLS` (Cache Purge + Cache Rules Read/Edit, this zone). Verified live and working on Surf City via `cf-cache-status`/`Age` headers (MISS-then-HIT pattern right after a real purge). This closes a real gap beyond the `status_code_ttl` fix above: a browser with an already-cached HTML page from the *old* build would otherwise keep referencing chunk filenames that no longer exist on either node post-deploy (since `deploy.sh` removes the old container) — a real, permanent 404 until this purge or the cache's natural TTL clears it.

**Decision at line 144 above (keep `strip_set_cookie` as-is, accept stickiness stays defeated) still stands** — if anything it's now on firmer footing, since the deploy-timing window that decision was weighing against has been shrunk from minutes to ~0-1 seconds by the pipeline fix, making the residual risk smaller than it was when that decision was made.

**Measured cost of the `purge_everything` step, 2026-09-29/30 — the penalty is ~9x worse for the Pakistan-based team than for US visitors.** Measured with raw HTTP fetches (no browser) from two locations simultaneously, forcing a cache MISS with a random *path* (note: Cloudflare ignores query strings in this zone's cache key, so `?cb=<rnd>` still returns HIT — use `/origin-probe-<rnd>`, which returns `308 BYPASS`):

- **From Pakistan**: cached HIT 34-44 ms vs origin 315 ms — **~9x penalty**
- **From a US host**: cached HIT 31-46 ms vs origin 68 ms — ~2.2x penalty

The asymmetry is just distance to the `us-west-2` origin. Practical consequences: (1) after every merge the site feels noticeably sluggish from Pakistan until the cache refills, which is expected behaviour and not a regression — don't chase it; (2) when benchmarking anything against these sites, note merge times, or a post-purge origin fetch will be misread as a slow client/server. Origin itself is healthy — 68 ms TTFB uncached from the US is a fine number, confirming the slow figure seen locally is transit, not the server. See [[project-fluten-rdp-box]] for the session where this was measured.

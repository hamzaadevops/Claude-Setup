**ALB/nginx gotcha, worth remembering for anyone touching this again:** the app containers publish their ports as `127.0.0.1:9000:9000` / `127.0.0.1:3000:3000` in `docker-compose.yml` — loopback-only, unreachable from the ALB even though nginx on the same box reaches them fine. Don't point an ALB target group at those raw ports; target nginx on 443 instead. **General rule for any future node added behind this ALB: every node needs `server_name` blocks + valid certs for *every* hostname the ALB might route to it** — this bit Node A once (missing `phn2`/`api2` vhosts caused ~50% of requests to 404 on every asset) and had to be fixed proactively on Node B before the `phn`/`api` cutover to avoid recurring. **CLI gotchas**: `aws elbv2`/`aws acm`/`aws ec2` calls with a leading-`/` argument get mangled by Git Bash's MSYS path conversion unless `MSYS_NO_PATHCONV=1` is exported first; `--matcher HttpCode=200,428` shorthand gets parsed as a list by the comma — use `--matcher '{"HttpCode":"200,428"}'` JSON instead. When adding/removing SG rules that gate live traffic (like the ALB/merged lockdowns above), always **add the replacement rule before revoking the old one** — never revoke first, even briefly.

**DNS-01 cert issuance pattern for hostnames behind the ALB** (needed since HTTP-01 can land on the wrong node): `certbot certonly --manual --preferred-challenges dns` normally requires interactive confirmation per domain, which doesn't work over non-interactive SSM. Worked around with a custom `--manual-auth-hook` script that writes `$CERTBOT_DOMAIN|$CERTBOT_VALIDATION` to a file and then polls for a "go" signal file before returning — lets the DNS TXT value be retrieved, handed to the user to add in Cloudflare, and released only once confirmed added. Certbot calls the hook once per SAN domain, sequentially (not in parallel), so a multi-domain cert means that many sequential rounds of "get value → user adds it → release."

## 2026-09-11: inventory slowness root-caused on all 3 VMs — REAL BUG FOUND (inventory Redis cache is written to one place and read from another)

**Context:** user reported inventory still slow after the dev team implemented pagination. Investigated by SSM into all 3 VMs (read-only). **Verdict: pagination was a UI-level fix only and could not have helped — the backend does identical work per request regardless of `limit`/`offset`.**

**THE PRIMARY BUG — two disjoint inventory caches, verified against the deployed image (`nisanweb-backend:latest`, commit `718f383`), not just the repo:**
- **Request path** (`InventoryViewSet._fetch_or_cache_inventory`, `apps/homenet_inventory/views/inventory/inventory.py:320-345`) builds its cache key from `{rooftop_collection, field_list, updated_since, inventory_filter}` — **no `dealership_id`** — and calls `self.redis_cache.get(cache_key)` / `.set(...)` with **no `dealership_id` argument**. `RedisCache._db_for_dealership(None)` therefore returns `_default_db()`, and `REDIS_DB` is **not set** in either node's `.env`, so the request path can only ever read/write **Redis db0**.
- **Celery cron** (`refresh_homenet_inventory_cache`, `tasks.py:640-660`) builds its key from `_inventory_cache_params(dealership_id, ...)` — **including `dealership_id`** — and calls `cache.set(..., dealership_id=dealership_id)`, which routes to the **per-dealership** Redis DB (db2 surfcity / db6 puentehills / db11 corona / db12 sanbernadino).
- **Result: different key hash AND different Redis DB. The hourly warm-up is 100% wasted for serving traffic.** Confirmed empirically: db0 held 4 blobs whose TTLs drain toward 0 and get rewritten by *user requests* (observed TTL 155/162/170s, then all four back at ~7150s minutes later); db2/6/11/12 held the cron's copies plus `inventory:sync_meta:v1:*` keys that only the cron writes. ~55MB of Redis holds two copies of the same data, half of it never read.
- **Consequence:** every ~2h (`HOMENET_CACHE_TTL_SECONDS=7200`) each rooftop's db0 entry expires and **a real end-user request pays a live HomeNet SOAP fetch** (`FETCH_TIMEOUT_SECONDS=30`, `MAX_RETRIES=2`, backoff). No stampede lock, so concurrent requests all miss and all fetch. This is the source of the catastrophic tail latency below.

**Quantified scale — all measured, not estimated:**
- **Inventory blobs are 5.4–7.9 MB of JSON each** (`STRLEN`: puentehills 7,900,932 B; sanbernadino 7,381,490; corona 6,675,230; surfcity 5,621,641). Vehicle counts from the cron log: puentehills **363**, sanbernadino 343, corona 307, surfcity 261 → **~21.8 KB per vehicle**.
- **Every inventory request Redis-`GET`s and `json.loads()` the entire multi-MB blob**, then filters/sorts/dedupes in pure Python, and only slices the page at the very end. Redis `SLOWLOG` is full of these: single `GET`s of the inventory keys taking **10,000–38,525 µs (10–38 ms)** — and Redis is single-threaded, so each one stalls Celery broker ops and JD Power lookups too. `cmdstat_get: calls=281712, usec_per_call=474`.
- **15,288 full-blob-loading requests/day across both nodes** (7,663 Node A + 7,625 Node B).
- **`retrieve()` (single VIN) also loads the whole blob** and linear-scans it — **4,653 of those per day** (2,381 + 2,272), all from Next.js SSR revalidating vehicle-detail pages. Pulling 7.9 MB to return one 23–38 KB vehicle.
- **`filter-options` runs the identical full pipeline a second time**, and is called *more* than the list endpoint (2,509 vs 1,890 on Node A). A real iPhone session in the log fired **three different `filter-options` calls inside one second** as filter state settled.
- Responses are huge even when paginated: `list_inventory?limit=10` returns **256–338 KB** (encrypted, so also uncacheable at the edge — `API_CRYPTO_MODE=required`, `/api/homenet/` is not in `API_CRYPTO_EXEMPT_PREFIXES`). Every call needs a CORS **preflight** first because of the `X-Crypto-Key` header — 2,315 `OPTIONS` today.

**User-facing latency, from ALB `TargetResponseTime` (6h window, real traffic):** p50 **26–49 ms** (fine — static/cached), p90 **0.23–1.64 s**, p99 **2.3–25.4 s**, max **6–60 s**. The **60.001677 s** max is gunicorn's `--timeout 60` firing. Maxima clustering at 26/29/30 s line up exactly with the 30 s HomeNet fetch cap. Two `upstream timed out` entries in nginx's error log today, both on `list_inventory`. **So the site is not uniformly slow — it has a brutal tail**, which is exactly what the cache-miss storm predicts.

**Secondary real findings:**
- **JD Power enrichment does one sequential Redis round-trip per row** (`enrich_rows_with_jdpower`, cache pass), i.e. **363 blocking `get_json()` calls** over the *pre-pagination* set whenever a request sorts or filters on price (`_get_filtered_rows` → `price_ordering_requested`). Not batched (no `MGET`/pipeline). Per-VIN cache coverage itself is now **complete** (367/363, 261/261, 307/307, 344/343) — earlier partial counts were mid-warm — but the cap warning `JD Power enrichment hit the per-request fetch cap (50)` still fired **14× in 6h**, so some requests are still doing 50 live JD Power HTTP calls (`JDPOWER_TIMEOUT=10`, 15 workers).

Also every SSR page endpoint is hit **twice, with and without trailing slash** (e.g. payment-calculator 836 + 765), i.e. an `APPEND_SLASH` redirect round-trip on every one.

### 2026-09-12: `limit_conn` audited across all 3 VMs — root cause was already fixed properly, deliberately left alone

**User asked whether `limit_conn` could be removed after repeated 503 "site down" incidents. Answer: no, and it does not need to be — someone already fixed the actual cause surgically.** `nginx.conf` on **Node A and Node B** now carries:
```nginx
map $arg__rsc $frontend_conn_key {
    default $binary_remote_addr;
    ~.      "";
}
limit_conn_zone $frontend_conn_key zone=conn:10m;
```
nginx does not count a connection whose key is an empty string, so **every Next.js RSC prefetch (`?_rsc=…`) is exempt from `limit_conn`** — which was the exact mechanism behind the 503 storms (one visitor's page load firing dozens of concurrent prefetches). This is a better fix than the 60→300 raise it accompanied.

**Two improvements identified and DELIBERATELY DEFERRED by the user (2026-09-12) — not bugs, not urgent, bundle into the next nginx change rather than a dedicated reload:**
1. **`limit_conn_status` is not set on any VM**, so `limit_conn` rejects with **503** while `limit_req_status 429` is set. 2. **`worker_rlimit_nofile` is unset on all 3 VMs.** `worker_connections 768` × 2 workers, but each worker's soft fd limit is **1024** (hard 524288). Every proxied request needs a client fd *and* an upstream fd, so a worker wanting 768 client connections needs ~1,536 fds and has 1,024. **Latent ceiling — currently at ~23 established connections, i.e. ~2% of capacity, so no urgency.** Becomes real if traffic grows or more dealerships are added. **Symptom to watch for: `too many open files` in the nginx error log, which would look like a hard outage. The fix is `worker_rlimit_nofile 8192`, NOT raising `worker_connections`** — raising connections without raising the fd limit makes it worse.

**Real YAML gotcha hit and fixed, worth remembering for any future edit to this file**: Bitbucket's own schema validator (and the Atlassian VS Code extension's linter) is **stricter than PyYAML** — it rejects an unquoted/plain YAML scalar containing an embedded `: ` (colon+space) inside a `script:` list item, e.g. `- echo "ERROR: something went wrong"`, because it's ambiguous with mapping syntax. **PyYAML's `safe_load` silently accepts these and gave false confidence** — every validation this session done via `yaml.safe_load` on a live node passed, but Bitbucket's real "Test your bitbucket-pipelines.yml" tool still reported `INVALID`, and a real pipeline run failed to even start until fixed. **Fix: wrap the offending line in a YAML literal block (`- |` + indented content) instead of leaving it a bare plain scalar** — block scalars are exempt from the colon-ambiguity rule entirely (confirmed: the pipelines' existing `STATUS="Pending"... case "$STATUS" in ... esac` polling loops, already under `|`, never had this problem). **This bug predates this session's edits** — two lines in the pre-existing `custom: revert-surfcity:` pipeline (written earlier this session, never actually run since it's a manually-triggered custom pipeline) had the identical issue and had silently been broken the whole time; fixed as part of the same pass. **If `bitbucket-pipelines.yml` is ever edited again in this repo and a script line contains a literal `: ` in its message text, always wrap it in `- |`, don't leave it bare** — `PyYAML` validation alone is not sufficient proof of correctness for this file; a real Bitbucket pipeline run (or the "Test your bitbucket-pipelines.yml" tool) is the only fully trustworthy check.

**Second real bug hit and fixed, from an actual pipeline failure log**: the `python:3.12-slim` image used by these pipeline steps **does not ship `curl` by default** — the new Cloudflare-purge steps (below) failed with `bash: curl: command not found` on the first real run. Fixed by adding `apt-get update -qq && apt-get install -y --no-install-recommends curl > /dev/null` as the first script line in both purge steps (same pattern the "Build & push image to ECR" step already used for `docker.io`). **Any future step added to this file that needs a binary not already installed by an earlier line in the same step must explicitly `apt-get install` it — nothing is preinstalled beyond what `pip install awscli` gives you.**

# Team VPN — Narrative History

## 2026-09-10 — Provisioned, running, one manual step left

**Why this exists:** Cloudflare-fronted dealership sites (ours and clients') are having Pakistan removed from their country allow-lists for security reasons. The team works from Pakistan and needs its traffic — browser and CLI/API tooling alike — to look like it's coming from the US, without per-site whitelist requests (which usually aren't even possible to obtain).

**Where it lives:** Reused the existing Dealerships AWS account (`409289617504`, `us-west-2`) rather than a new account/provider, since the user explicitly said isolation from production doesn't matter for this — only "don't touch any existing security group." So: brand-new subnet (`10.0.3.0/24`, its own route-table association, no route changes), brand-new security group, brand-new SSH key — zero shared resources with any Dealerships production SG/instance/role. See `[[project-dealerships-aws-migration]]` for the account's other resources this deliberately avoids touching.

**What it is:** One `t4g.micro` (arm64, cheaper than `t3.micro`, wg-easy supports arm64 fine) running `wg-easy` (WireGuard + a peer-management web UI) in Docker with `network_mode: host`. Full-tunnel design (`WG_ALLOWED_IPS=0.0.0.0/0,::/0`) so every client's entire connection — not just the browser — exits through this box's Elastic IP, `44.242.4.12`.

**Access model decision:** originally planned to manage the box via SSM Session Manager (no SSH port open at all, matching how the rest of this account's EC2 fleet is managed per `[[project-dealerships-aws-migration]]`). Creating the IAM role for that was **blocked by the Claude Code auto-mode permission classifier** — IAM changes are treated as sensitive regardless of scope. Asked the user; they chose plain SSH instead. So: TCP/22 is open in `team-vpn-sg`, but restricted to the admin's IP at setup time (`103.147.42.47/32`) — this will need updating if the admin's IP changes, or widening slightly if multiple admins need direct access (don't open it to `0.0.0.0/0`).

**Hit and fixed one real bug during bootstrap:** wg-easy's Docker Compose file used `network_mode: host` + a `sysctls:` block, which Docker/runc rejects (can't set network sysctls on a container sharing the host's network namespace). Fixed by setting `net.ipv4.ip_forward` and `net.ipv4.conf.all.src_valid_mark` directly on the host via `/etc/sysctl.d/` instead of through Compose. Full detail in `COMMAND_LOG.md`. Verified post-fix: WireGuard listening on UDP/51820, NAT masquerade correctly targeting the `10.8.0.0/24` VPN subnet out `eth0`, FORWARD chain accepting both directions on `wg0`.

**CLI gotcha, same class as ones already logged for the migration project:** `aws ec2 import-key-pair --public-key-material fileb://...` and `run-instances --user-data file://...` both failed to load the file via every path-format variant tried (forward slash, backslash, with/without `MSYS_NO_PATHCONV`, no-space paths). Worked around by base64-encoding the file content in bash and passing the string directly instead of a file reference — didn't chase the root cause further since the workaround is fast and reliable. Worth trying this pattern first for any future blob-parameter AWS CLI call from this Windows/Git-Bash setup.

**Not yet done, blocking full handoff:** wg-easy v15 ships as a Nuxt single-page app with no plain REST/tRPC endpoint discoverable by direct `curl` probing (tried `/api/session`, `/api/wireguard/client`, `/api/trpc/wireguard.getClients` — all 404). Its first-run setup wizard (`/setup/1`, creates the admin login) genuinely needs a browser. This environment has no browser automation tool (same constraint noted in `[[project-dealerships-aws-migration]]`). Left an SSH tunnel open (`ssh -i ~/.ssh/team-vpn -L 51821:localhost:51821 ubuntu@44.242.4.12`) for the user to open `http://localhost:51821` locally and complete setup, then add one peer per team member through that UI.

**Also not yet done:** no dealership site has been tested against this box's exit IP/ASN yet — do that with 1-2 real sites before handing WireGuard configs to the rest of the team, per the original plan's risk flag (datacenter ASNs aren't always treated the same as residential ones by bot/VPN detection layered on top of the plain country check).

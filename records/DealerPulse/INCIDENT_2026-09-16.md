# Incident — DealerPulse backend degraded, 2026-09-16

Investigated 2026-09-17 from nginx logs and container state on the droplet.
Everything below is **[verified]** unless labelled otherwise.

**Answer to "was the backend down yesterday": yes, it was degraded for roughly
three hours, and the voice path took the worst of it.** It was never stopped —
the containers stayed up. It stopped answering in time.

## 6. Diagnosis

Netdata has been running on this box for four months with ~129 days of
retention, so the metrics for the incident window survived even though the
container logs did not. They are conclusive about the *mechanism*, and narrow
the cause to one or two candidates.

### 6.1 Thread exhaustion — the mechanism

Process/thread count inside the backend container, from netdata
(`cgroup_dealerpulse_backend-web_blue-1.pids_current`):

| time (UTC) | threads |
|---|---|
| 19:30 | 12 |
| 19:55 | 12 |
| **20:20** | **26** |
| 20:45 | 51 |
| 21:10 | 76 |
| 21:35 | 101 |
| 22:00 | 127 |
| **22:25** | **142** |
| *(container replaced)* | |
| 2026-09-17 00:05 | 10 |

**Twelve threads, steady for hours, then a straight line up to 142 and no
recovery.** Threads were being taken and never given back. Each incoming request
grabbed a worker, blocked on something, and held it. Once they were all held,
everything else queued behind them and hit nginx's 60-second limit — which is
why endpoints as trivial as an `OPTIONS` preflight started timing out.

It never self-corrected. It ended when the container was replaced.

### 6.2 What the box was doing: nothing

Everything else was idle throughout:

| metric | during incident | verdict |
|---|---|---|
| CPU | **8–9%** flat (2 vCPU) | not CPU-bound |
| Load average | **0.07 – 0.76** | effectively idle |
| Container CPU throttling | **0 ns** | never hit the `cpus: 1.5` limit |
| Memory | 2.7–2.8 GB used, 4.5 GB cached | no pressure |
| iowait | ~0.05% | not disk |

The only CPU movement in the whole window is a spike at 22:15 — that is the
deploy, not the incident.

**A machine at 8% CPU and load 0.2 does not fail because it is busy.** It was
waiting.

### 6.3 What it was waiting on: network traffic collapsed

Bandwidth across the window (kbps):

| time (UTC) | received | sent |
|---|---|---|
| 19:30 | 143 | 179 |
| 20:00 | 319 | 309 |
| **20:30** | **35** | **27** |
| **21:00** | **18** | **8** |
| **21:30** | **18** | **13** |
| **22:00** | **23** | **40** |
| 22:30 | 737 | 213 ← deploy |
| 23:00 | 149 | 138 ← recovered |

Traffic fell to roughly **a tenth of baseline and stayed there** for the whole
incident, then returned to normal the moment the containers were replaced.

This is the important detail. If the backend had been waiting on *slow
responses*, data would still have been moving. Instead it had 142 threads open
and was barely exchanging bytes — connections established and idle, blocked
waiting for something that never came.

### 6.4 Why it could never recover on its own

This is the part that turns a glitch into a three-hour outage, and it is
configuration, not bad luck [verified in `server/coresite/settings/database.py`
and across the settings module]:

- **No `statement_timeout`.** A query that hangs, hangs forever.
- **No `lock_timeout`.** A request waiting on a row lock waits indefinitely.
- **No `connect_timeout`.** Opening a connection can block without limit.
- **No `CONN_MAX_AGE` and no connection pooling.**
- **No ASGI threadpool bound** — Python's default, so threads accumulate.
- **`ATOMIC_REQUESTS: True`** — every single request opens a transaction, so
  every blocked request is also a held transaction.

There is nothing anywhere in the stack that breaks a stuck database wait. The
only timeout in the entire request path is nginx's 60 seconds, and that only
disconnects the *client* — the thread behind it keeps waiting.

### 6.4a Why there is no "exact error" to find — and it is not for want of looking

With `doctl` (context `digitalocean`) we can now see the managed cluster itself.
The conclusion is uncomfortable but it is solid: **no component in this system was
configured to record what happened.**

> **Correction, 2026-09-18.** An earlier version of this section said the
> database's slow-query logging and idle-transaction timeout were **disabled**,
> based on `doctl databases configuration get`. That was wrong.
>
> **`doctl databases configuration get` returns only the values a user has
> overridden — not the settings actually in force.** Queried directly through
> `pg_settings` on the live cluster, the real values are:
>
> | setting | doctl reported | actually in force |
> |---|---|---|
> | `log_min_duration_statement` | `-1` (off) | **`1000` — ON, logs every query over 1s** |
> | `idle_in_transaction_session_timeout` | `0` (off) | **`86400000` (24 hours)** |
> | `log_connections` | not shown | **`on`** |
> | `log_disconnections` | not shown | **`on`** |
>
> **So PostgreSQL was recording throughout the incident** — every connection,
> every disconnection, and every statement over one second. The evidence was
> written. The open question is only whether DigitalOcean still retains it.

Where the evidence stands:

| recorder | state during the incident | availability |
|---|---|---|
| Application logs | Daphne logged request lines only; no exception raised | `web_green` (22:14–23:00) survives, contains zero tracebacks |
| Old container's logs | — | **gone** — container recreated at 23:47 (§6.6) |
| **PostgreSQL log** | **actively logging connections, disconnections and slow queries** | **unknown — depends on DO retention. This is the thing to go and get.** |
| `pg_stat_statements` | not installed (`installed_version = None`) | no query history exists |

**What to look for in the PostgreSQL log for 2026-09-16 20:00–23:00 UTC:**

1. `FATAL: sorry, too many clients already` — would confirm connection exhaustion.
2. `duration:` lines in the tens of seconds — would name the blocking query.
3. A burst of `connection received` with no matching `disconnection` — would
   confirm connections opening and never closing, which is the signature §6.1
   predicts.

If DigitalOcean's retention does not reach back two days, that evidence is lost —
but it existed, which is a materially different position from "nothing was ever
recorded".

`StatMonitorEnable` is `false` and `pg_stat_monitor` is available but not
installed, so no query-level history is retained between restarts. Installing
`pg_stat_statements` is a one-line `CREATE EXTENSION` and would give that
visibility going forward.

### 6.4a-1 The two-hour clock — why it lasted exactly as long as it did

[verified on host and inside the container, 2026-09-18]

```
/proc/sys/net/ipv4/tcp_keepalive_time    = 7200   (2 hours)
/proc/sys/net/ipv4/tcp_keepalive_intvl   = 75
/proc/sys/net/ipv4/tcp_keepalive_probes  = 9
```

These are the Linux defaults and nothing overrides them. A client blocked on a
TCP connection whose peer has stopped answering waits **two hours** before the
kernel even begins probing, then 9 probes at 75-second intervals — roughly
**2 hours 11 minutes** before the socket is declared dead and the thread is
released.

The incident began around **20:00** and was still accumulating threads at
**22:25**, ending when the deploy replaced the container at 22:14–23:47.

**That is the same clock.** Nothing in the application, the database or the web
server had any opinion about how long to wait, so the only timeout in the entire
system was the operating system's two-hour TCP keepalive — and the outage lasted
approximately that long. On the server side the cluster does set
`tcp_keepalives_idle = 180`, but that governs the database's detection of dead
*clients*, not the client's detection of a dead *server*.

This is strong corroboration for §6.4d: the connections were not refused, they
went silent, and the stack had no way to notice for two hours.

**Cluster events rule out the DigitalOcean side.** `doctl databases events list`
shows the last event on `dp2-live` was **2026-08-28** (routine maintenance and
master promotion). Nothing on 2026-09-16 — no maintenance, no failover, no
resize, no restart. Whatever happened, DigitalOcean did not do it.

So the exact error does not exist. It was never written down. That is the finding.

### 6.4c Confirmed from the code: one thread = one in-flight request

This was checked against the versions actually installed in the running container
(Django 6.0.2, asgiref 3.9.1, channels 4.3.0, daphne 4.2.1), not from
documentation.

**1. Every HTTP request gets its own thread pool.**
`django/core/handlers/asgi.py:166`:

```python
async with ThreadSensitiveContext():
```

and `asgiref/sync.py:72` documents exactly what that does:

> "By default, a single thread pool executor is shared within a process.
> The ThreadSensitiveContext() context manager may be used to specify **a thread
> pool per context**."

Django opens one per request. So the thread is held for the life of the request.

**2. Every view in the application is synchronous.** `async def` appears **zero**
times across `server/apps` outside the WebSocket consumers — including both hot
webhooks, `log_call_webhook` and `inbound_dynamic_variables_webhook`. Every one
therefore runs in a dedicated thread via `sync_to_async`.

**3. The application never creates threads itself.** No `threading.Thread`, no
`ThreadPoolExecutor`, no `concurrent.futures` anywhere in the codebase.

**4. The WebSocket consumers are all `AsyncWebsocketConsumer`**, so open sockets
do *not* each hold a thread. (An earlier hypothesis that they did is wrong.)

**Therefore the thread count is a direct measurement of concurrent, in-flight,
unfinished requests.** The netdata graph in §6.1 is not a proxy for the problem —
it *is* the problem, measured. At 22:25 there were roughly **142 requests
simultaneously stuck inside Django**, none of which had returned.

### 6.4d Why it was probably not connection-limit exhaustion

The obvious theory is that 142 concurrent requests exceeded the cluster's
`max_connections = 100` — Django holds one connection per request, there is no
pool and no `CONN_MAX_AGE`.

**The status codes argue against it.** When PostgreSQL refuses a connection it
fails *immediately* with `FATAL: sorry, too many clients already`; psycopg2 raises
`OperationalError` and Django returns **500**. Across the whole of 2026-09-16
there were **zero 500s** — the log contains 301, 404, 200, 499, 101, 302, 403,
400, 502, 504, 405 and nothing else.

So connections were not being *refused*. They were **hanging**.

That points at connections that were established and then silently stopped
answering — a dropped or half-open TCP session, which is consistent with network
traffic falling to a tenth of baseline while 142 threads sat waiting. With
`connect_timeout`, `statement_timeout` and TCP keepalives all unset (§6.4), a
socket that never answers is waited on forever. Every new request repeats it.
Nothing errors, so nothing is logged, so nothing appears anywhere.

**Still worth pulling the graph.** The connection count for
2026-09-16 20:00–23:00 UTC is in the DigitalOcean control panel under `dp2-live`
→ **Insights** (`doctl` does not expose it). If connections climbed and then
flat-lined rather than hitting 100, that confirms the hang; if they pinned at 100,
the simpler explanation wins after all.

### 6.5 What we still cannot prove

The mechanism is certain. The trigger is not.

The evidence points at the **managed PostgreSQL cluster** — a lock held by a long
transaction, connection-slot exhaustion, or cluster-side slowness would all
produce exactly this signature. XTime is a weaker candidate: its client does set
`timeout=30`, so those calls release their threads, though a booking path that
chains three of them can still exceed nginx's 60s.

**Settling it requires the DigitalOcean managed-database metrics for
2026-09-16 20:00–23:00 UTC** — connection count, lock waits, CPU. We do not have
access to that account. This is now the single most valuable thing to ask for,
and it is question B2/3 on the pre-move checklist.

### 6.6 Log coverage — corrected

> An earlier version of this document said the deploy "destroyed the evidence"
> and implied logs are not kept. That was too broad and it was challenged
> correctly. The accurate position is below.

**Docker log retention is configured and it works.** Both compose files set
`json-file` with `max-size: 50m` and `max-file: 5` — up to 250 MB per container.
Stopping a container does **not** delete its logs: `web_green` exited on
2026-09-16 and its full log is still on disk and readable.

What was actually lost, and why [verified 2026-09-17]:

| container | log covers | status |
|---|---|---|
| the blue instance serving 20:00–22:14 | — | **gone** |
| `web_green` (`2b798f`) | 22:14:33 → 23:48:12 | on disk, readable |
| `web_blue` (`0c2b3b`) | 23:47:37 → now | on disk, readable |

There are **13 containers and 13 log directories** on the box — no orphans. The
blue container that served the first two hours of the incident no longer exists,
so neither does its log.

**The mechanism is recreation, not stopping.** The pipeline's
`docker compose stop web_$ACTIVE` preserves logs. But the *next* deploy of that
same colour runs `docker compose up -d web_$COLOUR` with a new image tag, which
**recreates** the container — removing the old one and its logs. Here, blue served
until 22:14 and blue was redeployed at 23:47, so its logs survived the incident by
about 90 minutes and then went.

So the real retention rule is not "50 MB × 5". It is: **a container's logs live
until the next deploy of that same colour** — in practice two deploys, which at
this release cadence can be hours.

`web_blue`'s current log is 7.2 MB against a 50 MB rotation threshold, so
rotation has never even triggered. The size limits are not the constraint. The
container lifecycle is.

Two things still hold:

- **Nothing ships logs off the box.** Netdata collects metrics, not logs. Once a
  container goes, its history is unrecoverable.
- **The logs we do have say nothing useful.** `web_green` covers 22:14–23:00 of
  the incident and contains **no tracebacks and no exceptions at all**. Daphne
  logs request lines; the application logged nothing about why it was stuck.

The staging pipeline additionally runs `docker container prune -f`, which *would*
delete stopped containers and their logs. Production does not.

## 6a. What to fix

Ordered by how much they reduce the chance of a repeat. The first three are
application changes and belong to the backend team.

**1. Put a bound on database waits.** In `DATABASES['default']['OPTIONS']`:

```python
'connect_timeout': 5,
'options': '-c statement_timeout=25000 -c lock_timeout=5000',
```

A stuck query then fails in 25 seconds instead of holding a thread forever. This
one change converts this outage into a handful of 500s.

**2. Bound the thread pool.** Nothing caps it today, so a slow dependency
consumes the process. A bounded pool sheds load instead of accumulating it.

**3. Reconsider `ATOMIC_REQUESTS: True` on the webhook paths.** Wrapping a
webhook that calls XTime in a database transaction means a slow third party holds
a database transaction open. Those two failure domains should not be tied
together.

**4. Ship logs off the box** — infrastructure, ours. Retention is configured and
working (§6.6), but a container's history dies with the container, and that
happens on the next deploy of its colour. Shipping them elsewhere makes retention
a function of time rather than of release cadence.

**5. Alert on thread count and on 5xx rate.** Netdata is already collecting the
thread count that would have caught this at 20:20 rather than at the customer.
Nothing is watching it.

**6. Raise nginx `proxy_read_timeout` to 90s** — but only *after* item 1. Raising
it first would make the outage quieter without making it shorter.

**7. Turn on the database's own recorders.** Three cluster settings, all currently
disabled, all changeable with `doctl databases configuration update` — **not done,
needs approval**:

| setting | in force now | proposed | effect |
|---|---|---|---|
| `log_min_duration_statement` | `1000` — already on | keep | logs any query over 1s |
| `idle_in_transaction_session_timeout` | `86400000` (24h) | `60000` | kills a transaction left idle 60s, and logs it |
| `pg_stat_statements` | not installed | `CREATE EXTENSION` | retained query statistics — would have named the blocking query |

The logging is better than first reported. The gap is that the 24-hour
idle-transaction timeout is long enough to be no protection at all, and that no
query statistics are retained.

**9. Set TCP keepalives on the database connection.** This is the one that
directly addresses §6.4a-1. In `DATABASES['default']['OPTIONS']`:

```python
'keepalives': 1,
'keepalives_idle': 30,
'keepalives_interval': 10,
'keepalives_count': 3,
```

A dead connection is then detected in about a minute instead of two hours,
without touching system-wide sysctls. Combined with item 1, a silent database
connection becomes a brief error rather than a three-hour outage.

**8. Add a connection pool.** The cluster has none, and Django opens a fresh
connection per request against a 100-connection ceiling. A DigitalOcean connection
pool in `transaction` mode puts a bound on this and is a control-panel change, not
a code change.

## 7a. Credential exposure during this investigation

`doctl databases get` prints the cluster's full connection URI **including the
`doadmin` password in plaintext**. It was run on 2026-09-18 and the password is
now in that terminal's scrollback and in this session's transcript.

Nothing was compromised by it, but combined with §8 of `ARCHITECTURE.md` — the
cluster accepts connections from **anywhere on the internet**, with no trusted
sources — a leaked superuser password is total access. The password should be
treated as exposed and rotated, and the rotation is a good moment to stop using
`doadmin` for the application at all.

Use `doctl databases connection <id> --format Host,Port,User,Database` in future,
which omits the password.
